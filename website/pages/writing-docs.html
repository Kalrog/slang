Docs

Writing docs

Slang's documentation lives in ordinary comments. slang doc turns them into pages like these, and the language server shows them on hover, in completion and in signature help. The same comments work in your own modules: run slang doc in a project and it documents the project.

Where docs go

  • The comment block that starts a file documents the module: what it is for, a short example, what a reader needs to know first.
  • The comment block directly above a definition, with no blank line in between, documents it. Only what a module returns is its API.
  • // ---- title lines group the API into sections.
  • Lines indented by two spaces or more are code samples; the rest is prose, with `code` spans.

A definition's doc

// serve(host: string, port: int, handler: func(req: Request): any,
//       options?: ServeOptions) -> server: Server
// Serves HTTP on host:port until [Server.close]. The handler may return a
// Future: an async function works as one.
// [port]: 0 picks a free port
// [options]: limits and timeouts, see [ServeOptions]
// [server]: what is serving
func http.serve(host, port, handler, options){ ... }
  • The first line is the signature: the name as users call it, the parameters, then -> result. It may go on over lines until its parentheses close, and the -> may start the next line.
  • A parameter is name, name: Type, name?: Type (optional) or ...name (the rest).
  • The result is -> Type, -> name: Type, -> Type: what it is, or prose when no type says it.
  • [name]: text lines describe a parameter, the named result or a field. An indented line right below one continues it.
  • [name] in prose refers to a parameter, a type, a definition of the module, a method ([Server.close]) or another module's definition through the name the file gives it ([async.Future]). Pages link it; editors jump to it.
  • A method is documented without the value it is called on: close() for func server_methods.close(s).

Types

// What a handler receives. Header names are lowercase.
// type Request = {method: string, path: string,
//   headers: {[string]: string}, body?: string}
// [body]: the body, read whole

// A running server.
// type Server
local server_methods = {}
  • type Name = T declares a type on its own comment lines, and may span lines until its braces close. [field]: text lines under it describe its fields.
  • type Name alone, directly above a table, makes that table's functions the type's methods.
  • Type names are capitalized. Another module's type goes through the local the file binds the module to: async.Future.
  • The notation: string, int, float, bool, null, any, function, table, Name, mod.Name, T?, A | B, {T} (a list), {[K]: V} (a map), {a: T, b?: U} (fields), func(a: T): R.

Extensions

A file that changes the grammar (it gets require("slang/compiler").grammar() and returns no module) is documented as an extension. slang doc loads it into a fresh grammar and works out what it adds: the syntax as EBNF (new statements, rules, operators with their precedence, new kinds of expressions), the words it reserves and the extensions it loads. The doc comment says the rest:

  • The first paragraph is the summary: what the extension adds.
  • The rest explains what the syntax means: what it expands to, scoping, errors, edge cases.
  • Code samples are examples. Each must compile with the extension loaded (leave out the extension "..." line); its page shows what it expands to, and on this site examples run in the browser.
  • When the generated EBNF says too little (a custom parser shows as ⟨custom⟩), a paragraph that is just Syntax: followed by an indented EBNF block replaces it.
// enum NAME { Member, ... } declares a table whose members map to their
// own names, for use as symbolic values.
//
// Syntax:
//   statement ::= "enum" identifier "{" (identifier ("," identifier)*)? "}"
//
// The table is a local of the block the statement is in.
//
//   enum Color { Red, Green, Blue }
//   print(Color.Red, "\n")   // Red

Native modules

Modules written in Zig or C are documented by stubs: slang files that declare the module's functions with empty bodies and the same doc comments.
