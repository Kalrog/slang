slang/inline_test

slang/inline_test: tests next to the code they test, in the same file.

Load it at the top of a file with extension "slang/inline_test", or for every file of a project in slang.project: extensions: {"slang/inline_test"}. It changes the grammar of the files that load it only.

Syntax

statement ::= "group" "(" expr ")" block
a new statement (inline_group)
statement ::= "test" "(" expr ")" block
a new statement (inline_test)
statement ::= "setup" block
a new statement (inline_setup)
statement ::= "teardown" block
a new statement (inline_teardown)

How it works

group(name){ ... }, test(name){ ... }, setup{ ... } and teardown{ ... } are statements that mean what slang/test's t.group, t.test, t.setup and t.teardown do, written without the module: a setup runs before each test and subgroup of the group it is in, a teardown after each. They are only there when the file is compiled for a test run (see the grammar's testing()): slang test compiles the files of the project under test so, and its packages' and slang's library files not. In any other compile (slang run, slang build, a require from a program) these statements compile to nothing, and so do the locals and helpers written inside them.

The tests of a module register when the module is loaded in a test run: slang test file.slang runs the tests of that file (and those of the project's modules it requires), and a test file that requires a module runs the module's tests along with its own. A group or test at the top of a module joins the group being registered when it is required, so require modules at the top of a test file.

The words group, test, setup and teardown stay usable as names; a call test(x){ ... } or setup{ ... } with a block, though, is this statement in a file that loads the extension.
