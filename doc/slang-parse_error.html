slang/parse_error

slang/parse_error: parse failures as messages people can read.

A parse that fails knows the farthest position it reached and everything that was expected there (slang/grammar parses the statement again to collect it, see ctx.expected in slang/peg). describe turns that into a message, the position to report it at, notes at other positions and hints. The position is not always the farthest one: a bracket left open is reported where it was opened, a } that closes the wrong block where its indentation says a } is missing, an unclosed string where it starts, a missing ) at the end of the line instead of at the start of the next one. The hints name what other languages write that slang does not (&&, ++, function, while, ...).

local d = parse_error.describe(source, pos, {"Expected: )"})
// {message: "expected `)`, found `}`", pos: ..., notes: {...}, hints: {...}}

brackets

parse_error.resume_at(source: string, start: int, far: int) -> int

Where a parse that recovers from a statement starting at start, which failed at far, should go on: the next line after far where the brackets the statement opened are closed again (so that the body of a block whose header failed is skipped with it); -1 when they never close.

describe

parse_error.describe(source: string, pos: int, expected: {string}) -> Diagnosis

What a parse that failed at pos (its farthest failure) should say, given the messages of everything that was expected there.

parse_error.offset(source: string, line: int, column: int) -> int

The byte offset of a 1-based line and column.

parse_error.excerpt(source: string, pos: int) -> string

The line pos is on, numbered, with a caret under pos.

12 | local y = x +* 2
   |              ^

parse_error.report(source: string, origin: string, d: Diagnosis) -> table

The error to raise for d: {kind: "syntax", message, location, stack}, where stack (what a command line prints after the location) is the excerpt, the hints and the notes.
